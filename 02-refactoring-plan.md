# План рефакторинга

> В рамках лабораторной работы №2 код **не изменяется**. Документ описывает, что и в каком порядке будет сделано. Ссылки вида V1, A1 относятся к таблицам из `01-solid-analysis.md`.

## 1. Цели

* Устранить дефект с кодом `127` при неверном формате запуска (A1).
* Отделить бизнес-логику проверки доступа от интерфейса командной строки (V1, V10).
* Разделить ответственности и ввести абстракции для хранилища и хэширования (V3–V5, V7–V9).
* Навести порядок в структуре репозитория (A3–A5).

## 2. Принципы проведения

* **Поведение не меняется.** Внешний контракт (флаги, коды `0`–`8`) остаётся прежним, кроме исправления A1.
* **Маленькими шагами.** Каждый шаг заканчивается рабочей сборкой.
* **Страховочная сетка.** После каждого шага запускаются `bash scripts/build.sh` и `bash scripts/test.sh`; ожидаемый результат `9/9` (после шага 0 добавляются кейсы на неверный формат запуска).
* **Одно изменение — один коммит** в отдельной ветке, итог — pull request.

## 3. Шаги

### Шаг 0. Исправление дефекта кода `127` (A1)

* **Проблема:** `kotlinx-cli` при ошибке аргументов завершает процесс внутри `parser.parse`, `try/catch` не срабатывает.
* **Решение:** до вызова парсера самостоятельно проверить «форму» аргументов: ровно пять пар «флаг значение», все пять обязательных флагов присутствуют, значения не начинаются с `-`. Если форма неверна, вывести справку приложения и вернуть код `1`. Парсер вызывается только для заведомо корректных аргументов.
* **Проверка:** добавить в `test.sh` кейсы `--bogus` и `--login alice` (без остальных флагов), ожидаемый код `1`; убедиться, что код `127` нигде не появляется.
* **Риски:** значения, начинающиеся с `-` (например, пароль `-x`), будут считаться ошибкой формата; это нужно зафиксировать в `readme.md`.

### Шаг 1. Гигиена репозитория (A3, A4, A5)

* Создать `.gitignore`: `app.jar`, `build/`, `out/`.
* Удалить `app.jar` из индекса git: `git rm --cached app.jar`.
* Структура каталогов:
  ```
  src/        исходный код приложения
  tools/      вспомогательные инструменты (GenHash.kt)
  scripts/    build.sh, run.sh, test.sh
  lib/        kotlinx-cli-jvm-0.3.6.jar
  docs/       документация и планы
  readme.md
  ```
* Обновить пути в скриптах (переход в корень проекта, список исходников через `find src -name '*.kt'`).
* **Проверка:** сборка и тесты проходят с новой структурой.

### Шаг 2. Пакеты без изменения логики

* Добавить объявления `package` и разложить файлы по каталогам согласно `03-clean-architecture.md`.
* Логика не меняется, только перемещение и импорты.
* **Проверка:** `build.sh` и `test.sh`.

### Шаг 3. Результат вместо `null` и вынос бизнес-проверок (V1, A2)

* Ввести `AccessRequest` (необработанные строки: логин, пароль, действие, ресурс, объём), `AccessResult` (`Granted` или `Denied(reason)`) и `DenyReason` (по одной причине на каждый код отказа).
* Создать `CheckAccessUseCase` и перенести в него **всю** цепочку проверок, включая проверку превышения объёма.
* `execute` превращается в адаптер: разбор аргументов → `AccessRequest` → вызов use case → отображение `DenyReason` в `ExitCode`.
* **Проверка:** `9/9`, в `execute` не осталось доменных правил.

### Шаг 4. Порты и внедрение зависимостей (V4, V9, V10)

* В прикладном слое объявить интерфейсы `UserRepository`, `ResourceRepository`, `PasswordHasher`.
* Создать реализации `InMemoryUserRepository` и `InMemoryResourceRepository` (содержимое `Data.kt`).
* Use case принимает зависимости через конструктор; сборка графа объектов выполняется только в `main`.
* **Проверка:** `9/9`; use case можно создать с поддельными репозиториями.

### Шаг 5. Разделение `Auth` (V3, V7, A6)

* `PasswordHasher` (порт) и `Sha256PasswordHasher` (реализация).
* `SaltGenerator` с единственным экземпляром `SecureRandom`.
* `HexCodec` как отдельная утилита.
* В учётных данных хранить идентификатор алгоритма хэширования.
* **Проверка:** `9/9`; пароли пользователей проверяются как прежде.

### Шаг 6. Разделение `Access` и `User` (V5, V8)

* Value object `ResourcePath` (формат, разбор, проверка префикса).
* `PermissionPolicy` с проверкой наследования прав; принимает только права, а не `User` целиком.
* Разделить `User` на данные аутентификации (`Credentials`) и права (`Grant`).
* **Проверка:** `9/9`.

### Шаг 7. Перенос CLI-представления (V2)

* `ExitCode` перенести в пакет адаптера CLI; добавить `ExitCodeMapper` (`DenyReason` → `ExitCode`).
* Разбор строки действия (`"read"` → `Action`) вынести из доменного `Action`.
* **Проверка:** `9/9`.

### Шаг 8. Расширяемость проверок (V6), по желанию

* Оформить проверки use case как набор маленьких правил с общим интерфейсом.
* Выполнять только если количество проверок растёт; иначе оставить отдельные приватные функции в use case.

### Шаг 9. Тесты и документация

* Юнит-тесты use case с поддельными репозиториями (без системы сборки: простой запуск проверок из отдельной точки входа либо `kotlin-test` как внешний jar).
* Обновить `readme.md`: новая структура, правило для значений аргументов, описание архитектуры.

## 5. Риски и способы их снижения

| Риск | Снижение |
|------|----------|
| Сломать поведение при переносе кода | `test.sh` после каждого шага, малые коммиты |
| Переусложнение для небольшого проекта | Шаг 8 выполняется по необходимости; интерфейсы только там, где есть реальная подмена |

* В `execute`/`main` нет доменных правил; доменный и прикладной слои не импортируют `kotlinx.cli` и `kotlin.system.exitProcess`.
