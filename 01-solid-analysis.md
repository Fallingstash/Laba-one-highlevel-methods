# Анализ проекта: нарушения принципов SOLID

## 1. Область анализа

Ревизия кода лабораторной работы №1 (консольное приложение проверки доступа к ресурсам).
Анализируются файлы: `Main.kt`, `Models.kt`, `Auth.kt`, `Access.kt`, `Data.kt`.
`GenHash.kt` — вспомогательный инструмент, в приложение не входит.

Как устроен поток работы сейчас:

```
main → execute(args)
         ├─ разбор CLI (kotlinx-cli) и вывод справки
         ├─ Data.users[login]            (поиск пользователя)
         ├─ Auth.verify(...)             (пароль)
         ├─ Action.parse(...)            (действие)
         ├─ Access.parsePath / find      (формат пути, существование)
         ├─ Access.isAllowed(...)        (права)
         ├─ проверка объёма              (прямо в execute)
         └─ возврат ExitCode → exitProcess
```

Именно `execute` в `Main.kt` является центральной точкой, вокруг которой сосредоточена большая часть нарушений.

## 3. Детальный разбор

### V1. SRP: `execute` делает слишком много

* **Место:** `Main.kt`, функция `execute`.
* **Что нарушено:** принцип единственной ответственности. У функции несколько независимых причин для изменения:
  1. поменялся формат ввода (флаги, формат справки, другая библиотека разбора);
  2. поменялись бизнес-правила (порядок проверок, правило допустимого объёма);
  3. поменялась таблица кодов ответа.
* **Конкретно:** проверка превышения максимального объёма (`volume > resource.maxVolume`) — это доменное правило, но она расположена рядом с разбором CLI и выбором кода завершения. При смене способа ввода (например, HTTP вместо командной строки) эту проверку пришлось бы переносить вместе с адаптером запуска, хотя `Auth` и `Access` уже отделены.
* **Исправление:** вынести всю цепочку проверок запроса (логин, пароль, действие, формат, существование, права, объём) в отдельный прикладной компонент `CheckAccessUseCase`, который принимает `AccessRequest` и возвращает `AccessResult` (разрешено либо отказ с причиной). `execute` остаётся тонким адаптером: разобрал аргументы → вызвал use case → преобразовал причину отказа в `ExitCode`.

### V2. SRP: CLI-представление внутри доменных моделей

* **Место:** `Models.kt`, `enum class ExitCode` и поле `Action.flag`.
* **Что нарушено:** SRP. Файл моделей меняется и при изменении предметной области, и при изменении интерфейса командной строки. Коды возврата и строковые флаги (`"read"`, `"write"`) — детали CLI, а не предметной области.
* **Исправление:** перенести `ExitCode` в пакет CLI-адаптера; соответствие «строка → `Action`» вынести в адаптер (или в разбор запроса), а доменный `Action` оставить чистым перечислением.

### V3. SRP: `Auth` совмещает несколько задач

* **Место:** `Auth.kt`, `object Auth` (`generateSaltHex`, `hashHex`, `verify`) и приватные `toHex`/`hexToBytes`.
* **Что нарушено:** SRP. В одном объекте: генерация случайной соли, вычисление хэша, сравнение хэшей, кодирование hex. Причины изменения разные: политика хранения паролей, алгоритм хэширования, формат хранения.
* **Исправление:** выделить интерфейс `PasswordHasher` (`verify`), реализацию `Sha256PasswordHasher`, отдельный `SaltGenerator` и утилиту `HexCodec`.

### V4. SRP: `Data` одновременно хранилище и источник данных

* **Место:** `Data.kt`, `object Data` (`root`, `users`).
* **Что нарушено:** SRP. Объект содержит описание дерева ресурсов, пользователей, их соли, хэши и права, и сам же является глобальной точкой доступа.
* **Исправление:** разделить доступ и наполнение: интерфейсы `UserRepository` и `ResourceRepository` (в прикладном слое) и их in-memory реализации (в инфраструктуре), наполнение данными — отдельно от логики доступа.

### V5. SRP: `Access` объединяет три разные задачи

* **Место:** `Access.kt`, `object Access` (`parsePath`, `find`, `isAllowed`).
* **Что нарушено:** SRP. Валидация формата пути, навигация по дереву ресурсов и политика наследования прав — три разные причины изменения (изменится формат имён / структура хранения дерева / правила наследования).
* **Исправление:** value object `ResourcePath` (формат и разбор), поиск ресурса в репозитории ресурсов, политика прав `PermissionPolicy` (проверка с наследованием).

### V6. OCP: список проверок нельзя расширить без правки `execute`

* **Место:** `Main.kt`, `execute`: последовательность `?: return`.
* **Что нарушено:** принцип открытости/закрытости. Чтобы добавить новое правило (блокировка пользователя, срок действия прав, ограничение по времени), нужно изменить существующую функцию, рискуя сломать остальные проверки.
* **Исправление (вариант):** представить проверки как набор небольших правил с общим интерфейсом (`AccessCheck`), которые use case применяет по порядку. Добавление правила = добавление нового класса и регистрация в composition root.
* **Оговорка:** для текущего размера проекта это может быть избыточным. Практичный компромисс: оставить последовательность проверок в одном use case, но каждую проверку вынести в отдельную маленькую функцию.

### V7. OCP: алгоритм хэширования вшит в `Auth`

* **Место:** `Auth.kt`, `hashHex`: `MessageDigest.getInstance("SHA-256")`.
* **Что нарушено:** OCP. Замена на более стойкий алгоритм (PBKDF2, bcrypt, Argon2) требует правки `Auth`. Дополнительная проблема: сохранённые хэши в `Data` привязаны к конкретному алгоритму, а их формат не содержит идентификатора алгоритма.
* **Исправление:** интерфейс `PasswordHasher` с реализациями; в хранимых учётных данных держать идентификатор алгоритма, чтобы можно было поддерживать несколько алгоритмов при миграции.

### V8. ISP: `isAllowed` зависит от лишних данных

* **Место:** `Access.kt`, `isAllowed(user: User, path, action)`.
* **Что нарушено:** принцип разделения интерфейсов (в широком смысле: клиент не должен зависеть от того, что не использует). Метод принимает `User`, содержащий соль и хэш пароля, но использует только `user.grants`.
* **Исправление:** принимать только список прав (`List<Grant>`) либо отдельную сущность прав; разделить `User` на данные для аутентификации (учётные данные) и данные для авторизации (права).

### V9. ISP: `Data` — единая «толстая» точка доступа

* **Место:** `Data.kt`, `object Data`.
* **Что нарушено:** ISP. Код, которому нужны только пользователи (аутентификация) или только дерево ресурсов (поиск), вынужден зависеть от общего объекта со всем содержимым. Подменить одну часть, не затрагивая другую, нельзя.
* **Исправление:** два узких интерфейса: `UserRepository.findByLogin(login)` и `ResourceRepository.find(path)`.

### V10. DIP: высокоуровневая логика зависит от конкретных реализаций

* **Место:** `Main.kt`, `execute`, обращения к `Data.users`, `Auth.verify`, `Access.*`.
* **Что нарушено:** принцип инверсии зависимостей. Бизнес-сценарий («можно ли пользователю это действие») зависит от конкретных объектов: хранилища, алгоритма хэширования, реализации прав. Последствия:
  * нельзя подменить хранилище (файл, база данных) без правки `execute`;
  * нельзя протестировать сценарий с поддельными данными без реальных хэшей;
  * нельзя заменить алгоритм хэширования.
* **Исправление:** ввести абстракции (порты) `UserRepository`, `ResourceRepository`, `PasswordHasher` в прикладном слое; use case получает их через конструктор; создание конкретных объектов — только в `main` (composition root).

### LSP: нарушений нет

В проекте отсутствуют наследование и интерфейсы, поэтому нарушить принцип подстановки Барбары Лисков пока невозможно. Это не заслуга дизайна, а следствие отсутствия абстракций. После введения `PasswordHasher` и репозиториев реализации обязаны выполнять контракт:

* `findByLogin` возвращает `null` для неизвестного логина, а не бросает исключение;
* `verify` возвращает `false` для неверного пароля и не бросает исключение;
* `find(path)` возвращает `null` для несуществующего ресурса.

Любая реализация, нарушающая эти договорённости, сломает use case, то есть нарушит LSP.

## 4. Дополнительные замечания (не SOLID, выявленные при ревизии)

| № | Замечание | Место |
|---|-----------|-------|
| A1 | При неверном формате запуска `kotlinx-cli` завершает процесс сам (код `127`), `catch` вокруг `parser.parse` не срабатывает, справка выводится библиотекой, а не приложением. Код `127` вне таблицы `0`–`8` | `Main.kt`, `parseArgs` |
| A2 | Результат проверки теряет причину: `parsePath`, `find`, `Action.parse` возвращают `null`, вызывающий код сам восстанавливает смысл | `Access.kt`, `Models.kt` |
| A3 | Исходники лежат в корне репозитория вместе со скриптами, `readme.md` и вспомогательными файлами | структура репозитория |
| A4 | В репозитории находится собранный артефакт `app.jar` | корень репозитория |
| A5 | `GenHash.kt` (инструмент) хранится рядом с кодом приложения | корень репозитория |
| A6 | `SecureRandom()` создаётся при каждом вызове генерации соли | `Auth.kt`, `generateSaltHex` |
| A7 | Пароль передаётся в аргументах командной строки (виден в списке процессов и истории shell) — ограничение постановки задачи, но его стоит зафиксировать | постановка |

## 5. Приоритеты

Порядок важности исправлений (подробности — в `02-refactoring-plan.md`):

1. A1 — дефект поведения (код `127`), единственный пункт, влияющий на результат работы.
2. V1, V10 — главные архитектурные нарушения; их исправление открывает остальные.
3. V3, V4, V5, V8, V9 — разделение ответственностей и интерфейсов.
4. V2, V6, V7 — расширяемость.
5. A3–A6 — гигиена репозитория и мелкие улучшения.
