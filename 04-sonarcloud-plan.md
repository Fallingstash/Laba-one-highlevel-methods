# План интеграции SonarCloud

> Название: в 2025 году SonarCloud переименован в **SonarQube Cloud**. В документации и интерфейсе встречаются оба названия, речь об одном и том же сервисе. Ниже используется «SonarCloud», как в задании.

## 1. Цель

Подключить статический анализ кода к репозиторию так, чтобы при каждом push в основную ветку и при каждом pull request автоматически запускался анализ, а результат (проблемы, quality gate) отображался в PR.

## 2. Ограничения проекта, которые влияют на план

| Ограничение | Следствие |
|-------------|-----------|
| Системы сборки запрещены (Gradle, Maven) | Нельзя использовать готовые плагины `sonar` для Gradle/Maven; нужен универсальный сканер, запускаемый из GitHub Actions |
| Сборка делается через `build.sh` с `kotlinc` | В CI нужно установить JDK и компилятор Kotlin и выполнить тот же скрипт |
| Язык проекта — Kotlin | Нужно проверить поддержку анализатора Kotlin в выбранном режиме анализа |
| Покрытие тестами не измеряется (`test.sh` проверяет коды ответа) | Отчёт о покрытии на первом этапе не подключается |

## 3. Выбор способа анализа

SonarCloud предлагает два способа:

1. **Automatic Analysis** — анализ без CI: сервис сам читает исходники из репозитория.
2. **CI-based analysis** (через GitHub Actions) — анализ запускается в вашем CI после сборки.

**Выбор: CI-based через GitHub Actions.** Причины:
* в мастере создания проекта есть отдельный вариант «With GitHub Actions»;
* можно сначала собрать проект (`build.sh`) и передать сканеру скомпилированные классы, если анализатор их потребует;
* поведение анализа полностью описано в репозитории (файлы конфигурации под версионным контролем).

Automatic Analysis можно проверить как запасной вариант, если в интерфейсе для Kotlin он доступен.

## 4. Пошаговый план

### Шаг 1. Подготовка репозитория

* Репозиторий находится на GitHub; у участника, настраивающего интеграцию, есть права администратора.
* Работа ведётся в отдельной ветке (например, `feature/sonarcloud`), изменения оформляются pull request.
* Выполнены шаги плана рефакторинга, касающиеся структуры (`src/`, `scripts/`, `.gitignore`), либо пути в конфигурации ниже подставляются под текущую структуру.

### Шаг 2. Регистрация и организация

* Зайти на сайт SonarCloud (sonarcloud.io) и войти через учётную запись GitHub.
* Создать/импортировать организацию, соответствующую владельцу репозитория на GitHub, и установить GitHub-приложение SonarCloud с доступом к нужному репозиторию.
* Записать **ключ организации** (organization key).
* Уточнить условия тарифа: публичные репозитории обычно анализируются бесплатно, для приватных условия зависят от плана (проверить в интерфейсе).

### Шаг 3. Создание проекта

* В SonarCloud выбрать «Analyze new project» и выбрать репозиторий.
* На шаге «Choose your Analysis Method» выбрать **With GitHub Actions** и следовать подсказкам мастера.
* Записать **ключ проекта** (project key), обычно вида `<организация>_<репозиторий>`.

### Шаг 4. Токен и секрет

* Мастер выдаёт `SONAR_TOKEN`, он аутентифицирует запуск анализа в SonarCloud.
* В репозитории GitHub: *Settings → Secrets and variables → Actions → New repository secret*, имя `SONAR_TOKEN`, значение — полученный токен.
* Токен не хранится в репозитории и не печатается в логах.

### Шаг 5. Файл `sonar-project.properties` (в корне репозитория)

Метаданные проекта задаются в этом файле; организация и ключ проекта обязательны.

```properties
sonar.organization=<ключ организации>
sonar.projectKey=<ключ проекта>
sonar.projectName=Lab1 Access Control

sonar.sources=src
sonar.exclusions=lib/**,tools/**,build/**,out/**
sonar.sourceEncoding=UTF-8

# если анализатор потребует скомпилированные классы (проверить при первом запуске):
# sonar.java.binaries=build/classes
```

Пояснения:
* `sonar.sources` — только код приложения; сторонний jar и вспомогательные инструменты в анализ не входят;
* `sonar.java.binaries` включается, если анализатор сообщит, что ему нужны скомпилированные классы; каталог `build/classes` создаёт `build.sh`.

### Шаг 6. Workflow GitHub Actions

Файл `.github/workflows/sonar.yml`:

```yaml
name: SonarCloud

on:
  push:
    branches: [main]
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  analyze:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # полная история нужна для определения нового кода

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'

      - name: Install Kotlin compiler
        run: |
          curl -L -o kotlin.zip https://github.com/JetBrains/kotlin/releases/download/v<ВЕРСИЯ>/kotlin-compiler-<ВЕРСИЯ>.zip
          unzip -q kotlin.zip -d "$HOME"
          echo "$HOME/kotlinc/bin" >> "$GITHUB_PATH"

      - name: Build
        run: bash scripts/build.sh

      - name: Test
        run: bash scripts/test.sh

      - name: SonarCloud scan
        uses: SonarSource/sonarqube-scan-action@<ВЕРСИЯ ДЕЙСТВИЯ>
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

Замечания:
* Официальное действие `sonarcloud-github-action` объявлено устаревшим, его заменяет `sonarqube-scan-action` (полностью совместимая замена); используется второе.
* `<ВЕРСИЯ>` компилятора Kotlin берётся такой же, как при локальной сборке; точный адрес архива проверить на странице релизов Kotlin.
* Версию действия закрепить конкретной (тег или хэш коммита), а не плавающей.
* В официальном описании действия отмечено, что оно подходит не для всех технологий; применимость к Kotlin без системы сборки проверяется по результату первого запуска (см. раздел 6).

### Шаг 7. Quality gate и настройка проверки PR

* В проекте SonarCloud оставить стандартный quality gate (Sonar way) для нового кода.
* Включить комментирование/статус в pull request (SonarCloud добавляет статус quality gate как проверку GitHub).
* В *Settings → Branches → Branch protection rules* для основной ветки отметить статус SonarCloud как обязательный: слияние PR возможно только при пройденном quality gate.

### Шаг 8. Первый запуск и разбор результатов

* Создать PR с файлами конфигурации, дождаться выполнения workflow.
* Открыть проект в SonarCloud и посмотреть вкладки: Issues (баги, уязвимости, замечания по сопровождаемости), Security Hotspots, Measures.
* Для каждого замечания принять решение: исправить, пометить как ложное срабатывание или принять риск с обоснованием.

Ожидаемые темы замечаний для текущего кода (предположение, подтверждается только запуском):
* жёстко заданные данные для аутентификации (соль и хэши в `Data`);
* использование SHA-256 для хранения паролей;
* создание `SecureRandom` при каждом вызове;
* общие замечания по сложности функций и именованию.

### Шаг 9. Поддержка в рабочем режиме

* Анализ запускается автоматически на каждый push в основную ветку и на каждый PR.
* Правило команды: PR без пройденного quality gate не сливается.
* Токен обновляется при смене участников или подозрении на утечку.
* Документация: в `readme.md` добавить раздел о проверке качества и бейдж статуса.

## 5. Критерии готовности

* Проект существует в SonarCloud и привязан к репозиторию.
* Секрет `SONAR_TOKEN` добавлен, в репозитории его нет.
* Файлы `sonar-project.properties` и `.github/workflows/sonar.yml` находятся в репозитории.
* Workflow выполняется на PR и на push в основную ветку и завершается успешно.
* Результат анализа виден в SonarCloud, статус quality gate виден в PR.

## 6. Риски и открытые вопросы

| Риск / вопрос | Как снижаем / проверяем |
|---------------|--------------------------|
| Действие сканирования может не покрывать Kotlin без системы сборки | Проверить логи первого запуска; при необходимости указать `sonar.java.binaries`, либо проверить Automatic Analysis |
| Версия Kotlin и анализатор Sonar могут расходиться | Зафиксировать версию компилятора в workflow, сверить с поддерживаемыми версиями в документации SonarCloud |
| Секреты недоступны для PR из форков | Работать в ветках основного репозитория (как требует задание) |
| Покрытие не измеряется | Сознательно откладываем; при необходимости подключить JaCoCo как отдельный этап |
| Ограничения тарифа для приватных репозиториев | Проверить в интерфейсе на шаге 2 |
| Скачивание компилятора в CI зависит от доступности GitHub Releases | Закрепить версию; при проблемах кэшировать архив (`actions/cache`) |
| Переименование продукта (SonarCloud → SonarQube Cloud) | Опираться на актуальную документацию, учитывать оба названия при поиске |

## 7. Источники

* Репозиторий устаревшего `sonarcloud-github-action` (указание перейти на `sonarqube-scan-action`).
* Документация SonarQube Cloud: «CI-based analysis → GitHub Actions».
